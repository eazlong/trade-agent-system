# 统一的 halt 状态机是唯一的「停止」抽象，既有熔断器降格为触发源并保持禁用

代码里已有一个写得很完整的 `CircuitBreaker`（四条触发条件、trip/reset/record_failure 齐全），但它在 `RiskGuard.pre_trade_check` 里的调用点被注释掉了，实际上从不生效。我们决定**不**把它启用、也**不**把新的停止机制挂在它身上，而是引入一个独立的 halt 状态机作为唯一的「停止」抽象——已有的日内亏损、连续下单失败、API 断连、以及新增的行情阶段切换与事件熔断，全部降格为向它投递的**触发源**。唯一保留的改动是给既有熔断器接通「手动触发」入口。

## Considered Options

- **启用既有熔断器，把行情阶段/事件熔断作为它的第 5、6 条触发条件。** 被否决：`CircuitBreaker` 的模型是「同一 user 维度下的失败计数 + 自动 reset」，而事件熔断是带时间窗与作用域的、行情阶段停用是「自动停用 + 人工恢复」的——塞进失败计数模型会把三种语义完全不同的停止压成一种，且 reset 语义会互相干扰。
- **让新机制只做行情阶段与事件，既有的继续禁用、不管它。** 被否决：那就是三套并存的停止概念，而它们的语义差异没人能说清；「哪些检查是活着的」将只能靠读代码回答。

## Consequences

- **`CircuitBreaker` 的代码会继续留在仓库里且看起来是坏的**——它完整、可读，自动路径之外却没有调用点。这是刻意的：它的四条触发条件是真实需求（日内亏损、连续下单失败、API 断连、手动），将来会作为触发源接进新状态机，所以不删。**不要把它「修好」或接回 `pre_trade_check`**，那会造出第二个停止抽象。
- 停止的语义从「谁在拦」变成「谁投的触发源」，排查停用原因时必须能回答是哪个源、什么时候、依据什么。

## 兑现记录（2026-10-12）：手动触发入口已落地，落点是声明行

「接通手动触发入口」的欠账已还，但**落点与当年代码里的 Redis 键不同**：入口是 `manage.py manual_halt`（以及 `apps/regime/manual_halt.py` 的 `trip` / `lift`），效果是**一行 `HaltTrigger.MANUAL` 声明**（作用域同表三档：global / symbol / strategy，默认 24h 到点失效、可 `--hours 0` 到人工解除）。理由有三：

1. **判定函数只读声明表**（CONTEXT.md:134）。手动状态若留在 Redis，就得在 `halt.py` 之外开第二个读点才能拦单——那正是「绕过 halt 状态机的隐藏停机开关」；落声明表则走 `pre_trade_check` 第 0 步的同一个判定口，与事件熔断、保命档同一套答案。
2. **写出的状态有读者**（2026-10-12 评审第 4 条的整改点）：`halt.halt_layers` 求值、窗口通知（`halt_notify.notify_pending` 对声明行一律发「已生效 / 已解除」）、日报段、`query_halt` 全都读声明表——同源同句。
3. **`MANUAL` 没有开关**（`HALT_TRIGGER_SWITCH[MANUAL] = None`）：保命档「不需要确认就生效」，手动熔断「人已确认才生效」——两个方向、同一个结论：不再让任何机制开关否决一行已经认领的决定。

随之而来的两条边界：`halt_sync` 的对账**不认** `MANUAL`（不在 `_OWNED_TRIGGERS`），手动行活到人工解除（`--lift`）或自带 `expires_at` 到点失效为止；`CircuitBreaker` 的 `trip` / `is_open` / `reset` / `get_failure_count` 依然零调用点、零读点——既定状态未变，等「连续下单失败」等自动源接线时一并处置。
