# 池化表重算拆成独立 Celery 任务，而不是复用全链重算命令

机制今天唯一的重算入口是 `manage.py recompute_regime_slices`：切片 → 池化 → 差异重放，**串行、同步、分钟级**（该命令 docstring 记着实测：4067 条结果的陈旧扫描在 `.defer()` 修复前要 283 秒）。网页要一个「重算池化表」按钮，两条路：复用这条全链，或者只重建池化。

决定：**新写一个只跑 `pool_rebuild.rebuild_pool` 的 Celery 任务**（今天没有任何 Celery 任务包着它，唯一调用方是那条管理命令），Web 端点只投递任务并立刻返回，前端轮询 `RegimePoolRebuild.status`。按钮旁常驻一句「本操作只重建池化表；切片若已陈旧需另行跑 `recompute_regime_slices`」。

## Considered Options

- **复用全链 `recompute_regime_slices`（同步）**。被否决：分钟级的同步动作塞进 HTTP 请求，会造出一个「点了转圈五分钟然后 502」的按钮，而反代的超时不由我们决定。
- **复用全链（异步）**。被否决：那要求把一个既有管理命令包成任务，而它的三段（切片/池化/重放）各有各的失败语义与参数面（`--all/--result/--strategy/--limit/--force/--dry-run`）；给 Web 端暴露一个参数子集，等于在命令之上再造一层「哪些参数对网页有效」的判断，而那层判断迟早与命令漂移。
- **只重建池化但同步执行**。被否决：`rebuild_pool` 要遍历**全部** `BacktestResult` 的 `metrics`（`collect_samples()` 用 `iterator(chunk_size=200)` 扫全表），并对其中的每条样本做 sha256 指纹——规模随回测数量线性增长，同步执行在数据攒起来之后必然超时。
- **一个按钮刷新一切**。被否决：它更直觉，但它把「切片陈旧」这个前提藏起来了——用户会以为按下之后看到的结论就是最新的，而实际上切片可能是三天前的标签算的。

## Consequences

- **按钮有第四种收场：`reused`**。输入指纹命中时 `rebuild_pool` 不建代、不碰格子、**不留任何审计行**，只在命令 stdout 里说一句。网页必须把它与「新代就绪」分开显示，并写明「本次没有产生新记录」——把它显示成「已完成」就是让一个没写进审计的动作看起来像写过。
- **切片与池化的陈旧性是两条独立的轴，页面必须能分别回答**。池化表记录了自己用了哪几个回测结果（`RegimePoolCell.evidence.results`），而切片是否陈旧要问 `BacktestResult.metrics.regime_slice` 的版本。这个按钮只动前者。
- **并发触发有现成的答案，不要另写锁**：`uniq_pool_rebuild_ready_fingerprint` 会让第二个完成者撞上约束，`rebuild_pool` 把自己的那条记成带原因的 `failed` 行并如实返回（`duplicate=True`）。这是那条约束在起作用，不是故障——页面按「并发触发」显示，不按「失败」。
- **任务必须有可见的失败出口**：`CONTEXT.md:188` 要求新任务的失败走既有的两条路径（beat 任务健康检查 + 日报第④段）。这个任务是**人工投递**而非 beat 调度，所以它不进 `check_task_health` 的扫面——失败只能靠页面轮询到的 `failed` 行与日志。**这是本次接受的一个缺口**：如果投递成功但 worker 没跑，页面会永远显示「重算中」，而没有人会收到告警。可接受的代价是「重算失败」的后果是「表没更新」，不是资金动作；但它必须写在页面上（「超过 N 分钟仍在重算中，检查 worker」），否则一个卡死的 `building` 行会看起来像在正常工作。
- **`--dry-run` 语义在 Web 上不存在**：按钮就是真跑。预览「会重算哪些」需要另一条读路径，本次不做。
