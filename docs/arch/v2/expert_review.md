# 第2轮：专家交叉评审报告

> 评审对象：v1三份架构文档（agent_system.md / backtest_system.md / trading_execution_system.md）
> 评审角色：量化工程师 · 风控专家 · AI架构师
> 目标：找出冲突、漏洞、不一致，提出改进方向

---

## 一、量化工程师对v1架构的评审

### 1.1 对Agent系统（架构师A）的质疑

**[批评] CrewAI框架选型过重**
- CrewAI当前版本（0.x）对异步支持不完善，在高频事件驱动场景下会成为瓶颈
- 建议：核心路径用轻量级自研Agent基类 + asyncio，CrewAI仅用于对话式任务规划
- 替代方案：LangGraph（有向图状态机）更适合有明确状态转换的交易工作流

**[缺失] 市场数据实时订阅未定义**
- Agent如何获取实时价格？v1文档未定义
- 需要：WebSocket数据流 → Redis TimeSeries → Agent订阅机制
- 缺少：数据标准化层（不同交易所的ticker格式不一致）

**[冲突] 工作记忆TTL策略**
- v1定义工作记忆TTL=会话级，但交易决策需要跨会话的短期记忆（如：上一笔交易结果）
- 建议：分层记忆设计：会话级（Redis，TTL=2h）+ 交易级（Redis，TTL=7d）+ 长期（pgvector）

### 1.2 对回测系统（架构师B）的质疑

**[严重缺失] 前视偏差（Look-ahead Bias）防护**
- 回测引擎未说明如何防止使用未来数据
- 必须：每个bar只能访问当前及之前的数据，特征计算需严格时间对齐
- 建议：数据游标模式 + 特征时间戳强制校验

**[缺失] 手续费与滑点的真实模拟**
- 当前`slippage_bps`是全局固定值，不真实
- 真实滑点取决于：订单大小/市场深度/时间段（开盘/收盘流动性不同）
- 建议：基于历史订单簿深度的动态滑点模型

**[好评] 蒙特卡洛模拟设计合理**
- 随机排列历史交易序列的方法可以评估策略的统计稳健性
- 建议增加：Bootstrap抽样（有放回）以更好地估计参数不确定性

**[缺失] 策略持久化与版本管理**
- BacktestRequest.strategy_id指向什么存储？
- 需要：策略代码版本快照（Git-backed），回测结果与策略版本强绑定

### 1.3 对交易执行系统（架构师C）的质疑

**[好评] 幂等性设计正确**
- request_id作为幂等键是正确做法，可防止网络重试导致重复下单

**[缺失] 部分成交处理**
- OrderLifecycleManager定义了PARTIAL状态，但未说明如何处理：
  - 部分成交后取消剩余？
  - 等待完全成交？
  - 超时后强制市价成交剩余？
- 这对实际交易影响巨大

**[冲突] 紧急平仓的原子性问题**
- 多仓位并发平仓时，如果部分成功部分失败，Redis仓位缓存与实际持仓不一致
- 需要：定期从交易所同步真实持仓（reconciliation），不能只依赖Redis

## 二、风控专家对v1架构的评审

### 2.1 风控规则的独立性不足

**[严重] RiskGuard不应依赖Agent系统存活**
- v1中RiskGuard是Agent系统的一部分，如果Agent服务崩溃，风控也随之失效
- **强制要求**：RiskGuard必须是独立部署的微服务，与Agent系统完全解耦
- RiskGuard崩溃时：立即触发全局熔断（交易所适配器层的硬编码开关）

### 2.2 风控规则硬编码 vs 可配置的边界

**[建议] 区分「硬限制」和「软限制」**
```
硬限制（代码层，不可通过任何方式绕过）：
- 单笔亏损上限 = 账户净值5%（绝对上限）
- 总仓位杠杆 ≤ 20x
- 账户净值跌破初始值50%时强制清仓

软限制（数据库配置，管理员可调整）：
- 日亏损预警阈值
- 连续亏损告警次数
- 仓位建议上限
```

### 2.3 断网/宕机场景处理不完整

**[缺失] 需要明确以下场景的处理预案：**

| 场景 | 当前方案 | 建议补充 |
|------|---------|----------|
| 交易所API断线 | 未定义 | 挂预设止损单（交易所服务器端），不依赖本系统 |
| 数据库宕机 | 未定义 | 只读模式 + 禁止开仓 |
| Redis宕机 | 未定义 | 从交易所实时查询持仓（降级模式）|
| 服务器断电 | 未定义 | 交易所端预置OCO订单（止盈止损同时挂单）|

### 2.4 用户权限与多账户隔离

**[严重缺失] v1三份文档均未涉及**
- 用户A的Agent不能访问用户B的数据/仓位
- API Key需要账户级隔离（不同账户使用不同加密密钥？）
- 管理员操作需要审计日志（谁在何时修改了风控参数）

## 三、AI架构师对v1架构的评审

### 3.1 LLM调用成本控制缺失

**[缺失] v1未定义LLM调用策略**
- 每次行情变化都调用LLM会产生巨额API费用
- 需要：分层决策（规则引擎优先，LLM仅用于复杂判断）
- 建议：Token预算管理，每日/每用户LLM调用上限

### 3.2 Prompt工程缺失

**[缺失] Agent系统文档未定义Prompt结构**
- 每个Agent需要明确定义：系统Prompt、上下文注入方式、输出格式约束
- 输出格式必须结构化（JSON Schema），防止LLM返回无法解析的自由文本
- 需要：Prompt版本管理（Prompt变更会影响策略行为）

### 3.3 长上下文与记忆检索策略

**[建议] pgvector检索策略需细化**
- 当前仅说「语义检索」，需明确：
  - Embedding模型：text-embedding-3-small（成本低）还是本地模型（隐私）？
  - 检索topK：检索太多增加噪声，太少丢失关键信息
  - 记忆写入时机：每次对话结束？还是仅在重要决策点？

### 3.4 Agent输出的可信度验证

**[建议] Agent决策需要二次校验**
- LLM输出的交易指令可能格式错误、数值异常（如：买入1000个BTC）
- 需要：输出Schema校验 + 合理性检查（数量/价格范围校验）
- 建议：Santa Method（双Agent对抗验证）用于关键交易决策

## 五、v2架构调整方向总结

### 架构拓扑变化

```
v1（单体倾向）：
  Django → SupervisorAgent → [各子Agent] → RiskGuard → 交易所

v2（微服务化）：
  Django → MessageBroker(Redis Stream) → [各子Agent服务]
                                        → RiskGuard服务（独立）
                                        → 交易执行服务（独立）
                                        → 数据服务（独立）
```

### 关键设计原则调整

1. **RiskGuard优先原则**：所有资金操作必须经过独立RiskGuard服务，任何单点故障不影响风控能力
2. **防御性执行原则**：宁可误判不执行，也不能在异常状态下执行交易
3. **数据一致性原则**：Redis仓位缓存仅为加速读取，交易所持仓数据为唯一真实来源（定时对账）
4. **成本意识原则**：LLM调用需要预算控制，规则引擎覆盖80%的常规场景
