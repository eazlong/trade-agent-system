## 一、产品经理视角

### 1.1 严重缺失的核心功能

**用户身份认证与权限分级**
多账号系统没有展开。不同角色（观察者/交易员/管理员）的权限，API Key 加密存储方案，账号之间的数据隔离机制，涉及资金安全，不可后补。

**风控强制执行机制**
「风控（强制执行）」只是标题，缺失细节：
- 单笔最大亏损阈值自动平仓
- 日/周最大回撤熔断机制
- 仓位上限硬限制（不可绕过）
- 强制执行优先级高于任何智能体指令
- 断网/宕机时的安全处置方案

**智能体版本管理与回滚**
系统会随交易数据持续优化，但没有版本快照机制。策略和智能体需要 Git 式版本管理。

**提醒与通知渠道**
「发出提醒」未指定渠道（Telegram/邮件/Push/微信企业号/短信），需定义优先级和降级策略。

**资金管理计算器**
Kelly 公式仓位计算、固定比例风险、固定仓位三种主流方式，应内置并与交易计划强绑定。

**数据审计日志**
所有智能体决策链路必须可追溯，「为什么发出这个入场信号」需完整推理日志。

### 1.2 用户旅程 — 摩擦点分析

```
注册 → 连接交易所API → 通过对话建立交易系统 → 首次回测 → 测试盘验证 → 实盘

摩擦点：
1. API Key 配置（新手障碍最大）→ 需要图文引导 + 权限检查工具
2. 交易系统建立对话（问题太专业）→ 需要模板/示例交易系统
3. 回测结果解读（指标不懂）→ 需要智能解读层
4. 测试盘 vs 实盘切换（心理门槛）→ 需要明确的「毕业条件」引导
```

### 1.3 功能优先级

**MVP（第一期必须有）：**
- 对话建立交易系统（结构化JSON存储）
- 基础回测（支持币安历史数据）
- 风控强制执行（止损/日亏损上限）
- API Key 安全托管
- 信号提醒（至少支持Telegram）
- 主管Agent + 量化工程师Agent

**第二期迭代：**
- 自动生成入场前Checklist
- 交易总结与自动分析
- TradingView Webhook 集成
- 测试盘
- 舆情/链数据 Agent

**第三期迭代：**
- 系统自动研发策略
- 实盘自动下单
- 多账号管理
- 美股/A股/港股/期货支持

### 1.4 用户分层

| 用户类型 | 特征 | 核心需求 |
|---------|------|--------|
| 新手交易者 | 无系统，靠感觉 | 被引导建立系统，有模板，有教练 |
| 有系统的散户 | 有方法但执行差 | Checklist强制执行，自动复盘，打断情绪交易 |
| 量化爱好者 | 会写代码 | 策略开发/回测框架，数据API，策略优化 |
| 职业交易员 | 专职，有组合 | 多账号，多策略，组合风控，高级分析 |

### 1.5 商业化路径

1. **订阅制分层**：基础版（1个策略/1个交易所）/ 专业版（不限策略+高级Agent）/ 机构版
2. **按使用量计费**：API调用次数、回测次数、AI对话次数
3. **策略市场**：用户发布策略，按订阅分成
4. **数据服务**：高质量链数据/舆情数据订阅

### 3.3 记忆系统设计

```
记忆层级：

1. 工作记忆（Working Memory）
   - 存储：Redis（TTL=会话时长）
   - 内容：当前对话上下文、当前交易计划草稿
   
2. 情节记忆（Episodic Memory）  
   - 存储：PostgreSQL + pgvector
   - 内容：历史交易记录、历史对话摘要、用户反馈
   - 检索：向量相似度搜索（"上次讨论BTC策略时..."）
   
3. 语义记忆（Semantic Memory）
   - 存储：向量数据库（Chroma/Qdrant）
   - 内容：用户交易系统规则、策略代码库、市场知识
   
4. 程序记忆（Procedural Memory）
   - 存储：数据库结构化存储
   - 内容：用户确认的交易系统参数（JSON Schema）
   - 关键：这是Checklist生成和入场审核的核心依据
```

## 四、交易专家视角

### 4.1 完整交易系统的七大支柱

系统对话引导用户建立交易系统时，必须覆盖这七个维度（需求文档仅提到部分）：

1. **标的选择逻辑**（What to trade）
2. **入场信号**（When to enter）
3. **止损设定**（How much to risk）
4. **仓位管理**（How much size）
5. **出场机制**（When to exit，含止盈）
6. **市场环境过滤**（在什么行情里不交易）← 需求文档完全缺失
7. **资金管理规则**（账户层面的总风控）

### 4.2 对话问询的正确顺序

```
第一步：交易哲学确认
  - 交易风格：趋势跟踪/均值回归/突破/套利？
  - 持仓周期：日内/波段/中长期？
  - 最大单笔亏损比例（占账户%）？
  - 每天/周能盯盘多少小时？

第二步：市场与标的
  - 交易什么市场？什么标的？
  - 流动性要求（最低成交量）？

第三步：市场状态过滤（最常被忽略的关键步骤）
  -  - 策略在什么市场状态有效（趋势/震荡/高波动/低波动）？
  - 如何判断当前市场状态？

第四步：入场条件（至少2-3个确认条件）
  - 主信号是什么？（价格行为/指标/K线形态）
  - 辅助确认条件？
  - 多周期共振要求？

第五步：止损
  - 止损类型：固定点位/ATR倍数/结构性止损/时间止损？
  - 止损是否移动？何时移动？

第六步：仓位管理
  - 计算方式：固定比例风险（推荐）/固定手数/凯利公式？
  - 单次最大风险：账户的1%/2%？
  - 是否允许加仓？加仓规则？

第七步：出场管理
  - 止盈目标：固定R倍数/目标位/追踪止盈？
  - 部分平仓规则？

第八步：交易日志与复盘规则（最重要但最常被忽略）
```

### 4.3 入场前 Checklist 的四层设计

**Layer 1：宏观环境检查（每日开盘前）**
- 今日有无重大数据/新闻（FOMC/CPI/财报等）？
- 当前市场情绪（Fear&Greed指数/VIX/加密恐惧贪婪指数）？
- 过去24小时重大事件？

**Layer 2：标的分析（交易前）**
- 当前价格在哪个重要结构位附近？
- 该标的过去7天波动率是否异常？
- 多周期趋势方向是否一致？

**Layer 3：信号确认（发现机会时）**
- 入场信号是否满足交易系统全部条件？
- 当前是否处于有利的市场状态？
- 止损位是否合理（不会被正常波动打掉）？

**Layer 4：风控最终确认（下单前）**
- 仓位计算是否正确（基于当前账户净值）？
- 加上此单后总持仓风险是否超过上限？
- 今日亏损是否已达到日内止损上限？

### 4.4 交易后复盘的标准化框架

```
每笔交易复盘必须包含：
1. 入场是否符合系统规则？（是/否，偏差原因）
2. 止损设置是否合理？
3. 出场是否符合规则？（还是情绪驱动提前离场/持仓过久）
4. 此交易的期望值是正的吗？（即使亏损，只要执行正确就是好交易）
5. 如果重来一次，你会怎么做？

AI自动分析应额外提供：
- 入场时机评分（0-100）
- 仓位管理评分
- 执行纪律评分
- 与历史同类交易的对比
- 市场回放（入场/出场在K线图上标注）
```

### 4.5 需求文档中交易逻辑的关键缺陷

1. **缺少市场状态过滤器**：任何策略都有其有效的市场环境，在错误市场环境下执行正确策略同样会亏损
2. **缺少多周期分析框架**：只看一个时间周期是散户常见错误，系统应强制要求多周期确认
3. **缺少交易日志结构化设计**：自由文本的交易日志无法被AI有效分析，需要结构化字段
4. **缺少情绪管理机制**：连续亏损时强制冷静期，达到日亏损上限后自动锁定当日交易权限

## 五、风控专家视角

### 5.1 风控强制执行的技术实现

**核心原则：风控层必须在执行层之前，且不可绕过**

```python
class RiskGuardian:
    """所有交易指令的必经关卡，优先级高于任何Agent"""
    
    HARD_LIMITS = {
        "max_single_loss_pct": 0.02,      # 单笔最大亏损2%
        "max_daily_loss_pct": 0.06,       # 日最大亏损6%
        "max_drawdown_pct": 0.15,         # 最大回撤15%（触发暂停）
        "max_position_concentration": 0.3, # 单标的最大仓位30%
        "max_leverage": 3.0,              # 最大杠杆3倍
    }
    
    def validate_order(self, order: Order, account: Account) -> ValidationResult:
        checks = [
            self._check_daily_loss_limit(account),
            self._check_drawdown_limit(account),
            self._check_position_concentration(order, account),
            self._check_leverage_limit(order, account),
            self._check_single_order_risk(order, account),
        ]
        failed = [c for c in checks if not c.passed]
        if failed:
            return ValidationResult(blocked=True, reasons=failed)
        return ValidationResult(blocked=False)
    
    def emergency_stop(self, account_id: str, reason: str):
        """紧急停止：取消所有挂单，平掉所有仓位"""
        # 这个方法任何Agent都不能阻止
        pass
```

### 5.2 风控指标体系

| 风控维度 | 硬限制（强制执行） | 软限制（警告提醒） |
|---------|----------|----------|
| 单笔亏损 | 账户净值2% | 账户净值1.5% |
| 日亏损 | 账户净值6% | 账户净值4% |
| 最大回撤 | 15%（暂停交易） | 10%（加强复盘） |
| 单标的仓位 | 30% | 20% |
| 总杠杆 | 3倍 | 2倍 |
| 连续亏损笔数 | 5笔（强制冷静期24h） | 3笔（提醒复盘） |

### 5.3 API密钥安全方案

```
存储方案（分层加密）：
1. 用户密码派生密钥（PBKDF2/Argon2）
2. 用密钥对API Key/Secret加密（AES-256-GCM）
3. 加密后密文存数据库，明文从不落盘
4. 运行时在内存中短暂解密，用完即清除

权限最小化原则：
- 只申请「只读」+「现货交易」权限
- 明确禁止「提币」权限
- 明确禁止「杠杆借贷」权限（除非用户明确开启）
- IP白名单绑定服务器IP

安全审计：
- 记录每次API密钥使用时间和操作
- 异常地理位置访问告警
- 定期提醒用户轮换API密钥
```

### 5.4 系统故障保护机制

```
故障场景 → 保护措施：

网络中断：
  → 已挂单：保留（交易所侧）
  → 监控脚本：降级到轮询模式
  → 用户：立即Telegram告警
  → 恢复后：自动同步持仓状态

API失效（限流/封禁）：
  → 所有下单指令暂停
  → 保留当前仓位（不自动平仓，避免滑点损失）
  → 用户告警 + 等待人工介入

系统崩溃（进程死亡）：
  → 心跳监控（每30秒）
  → 自动重启（最多3次，超过则告警等待人工）
  → 重启后首先同步持仓，再恢复监控
  → 所有未确认订单标记为「需核查」

交易所宕机：
  → 本地缓存最后持仓状态
  → 暂停新信号执行
  → 定期重试连接
```

### 5.5 需求文档风控最大缺失

1. **紧急平仓机制未定义**：极端行情下（闪崩/爆仓风险）需要一键全平的紧急出口
2. **多账号风险合并计算**：多账号场景下需要汇总全局风险敞口，而非各自独立计算
3. **策略相关性风险**：多策略同时运行时可能持有高度相关的头寸，需要组合层面的风险控制
4.**回测过拟合风险**：系统自动研发策略时需要防止过度优化（曲线拟合），必须强制要求样本外测试
5. **法律免责边界**：系统提供的是「工具」而非「建议」，界面需要明确的免责声明

1. **通信层**：Agent间使用 Redis Stream（已有Redis，直接用）

3. **回测引擎**：加密货币用VectorBT，股票用Backtrader适配层
